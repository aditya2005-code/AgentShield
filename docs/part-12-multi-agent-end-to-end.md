# Part 12 — Full Multi-Agent End-to-End System Integration Documentation

This document summarizes the full multi-agent orchestration, agent selection flow, failure resilience, and conflict resolution rules implemented in the AgentShield system.

---

## 1. Final Complete System Architecture

```
                 Transaction or Customer Event Ingestion
                                   ↓
                       POST /agentshield/process-event
                                   ↓
                   (process_event_orchestration service)
                                   ↓
                    [Applicable Agent Selection rules]
                                   │
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
         Fraud Agent        Recovery Agent        Growth Agent
         (TRANSACTION)     (PAYMENT_FAILURE)   (GROWTH_OPPORTUNITY)
              │                    │                    │
          (In-Memory)        (Merchant RAG)       (Merchant RAG)
          Fraud ML           Policy Retrieval     Policy Retrieval
              │                    │                    │
          Gemini LLM           Gemini LLM           Gemini LLM
              │                    │                    │
              └────────────────────┼────────────────────┘
                                   ↓
                        Independent Proposals
                                   ↓
                       evaluate_proposal (AgentShield)
                                   ↓
                          [Conflict Resolution]
                       REJECT > ESCALATE > MODIFY > APPROVE
                                   ↓
                       Aggregated Final Decision
                                   ↓
                        ShieldDecision & Audit Log
```

## 2. Event → Agent Selection Flow

Applicable agents are selected dynamically using the event type and current database state:

- **`TRANSACTION` Event**:
  - `FraudAgent` (always applicable).
  - `RecoveryAgent` (applicable if status is `FAILED` or `BLOCKED`).
  - `GrowthAgent` (applicable if status is `SUCCESS`).
- **`PAYMENT_FAILURE` Event**:
  - `RecoveryAgent` (always applicable).
  - `FraudAgent` (applicable as payment failures can indicate underlying fraud risk).
- **`GROWTH_OPPORTUNITY` Event**:
  - `GrowthAgent` (always applicable, using customer context).

---

## 3. Core Component Integrations

- **Fraud ML**: Extracted features are processed by the cached model, and the risk classifier inserts raw metrics in `action_parameters` and the Gemini context.
- **Recovery RAG**: Synchronously retrieves policy rules specific to the transaction's merchant context and includes them in the Recovery Agent prompt.
- **Growth RAG**: Scopes VIP loyalty or abandoned cart policies to the customer's merchant, avoiding cross-merchant leakage.

---

## 4. Multi-Agent Proposal Collection & Deduplication

- The orchestrator collects proposals generated by all executed agents for a single event.
- Idempotency checks are run before agent execution to return existing pending proposals, preventing duplicate runs from creating duplicate database entries.
- Proposals remain distinct, mapped to their specific agent type and the event ID.

---

## 5. Conflict Resolution Behavior

When multiple agents propose different actions (e.g. Fraud proposes `BLOCK_TRANSACTION` and Recovery proposes `WAIT_AND_RETRY`), the orchestrator resolves conflicts based on the following priority rules:

1. **`REJECT`**: Proposing protective actions that fail guardrails immediately rejects the workflow.
2. **`ESCALATE`**: If any proposal requires human review (such as blocking customer access), the entire workflow is escalated.
3. **`MODIFY`**: If no blocks are present but policies require modification (exceeding discount limits), the parameters are modified.
4. **`APPROVE`**: Appoved if all proposals pass guardrails cleanly.

---

## 6. Agent Failure Resilience

If any optional agent fails during execution (e.g. Gemini quota limits, ML loading error, or database state mismatches), the orchestrator:
1. Logs the traceback safely using standard python logger.
2. Continues executing other applicable agents.
3. Sets event status to `DEGRADED` but still completes successfully and evaluates the remaining proposals.
4. Exposes no credentials, keys, or stack traces to the API consumer.

---

## 7. Tenant Isolation

RAG queries strictly scope database operations to `merchant_id` retrieved from the transaction or customer records. Merchant A events can never retrieve policies or proposals belonging to Merchant B.
